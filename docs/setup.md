# Подготовка окружения

## Текущее состояние

Репозиторий содержит код, зависимости в манифестах и SQL-экспорт из локальной PostgreSQL **17.5**:

- [database/schema.sql](../database/schema.sql) — схема `pizzeria`: 22 таблицы, включая все таблицы Identity и `__EFMigrationsHistory`, одно представление, две функции, пять enum-типов, последовательности, индексы, ограничения и триггер. Записей клиентов, заказов и пользователей в файле нет.
- [database/migrations-history.sql](../database/migrations-history.sql) — пять фактических записей `MigrationId` / `ProductVersion` из истории EF. Это только технические метаданные.

**Восстановление `schema.sql` и `migrations-history.sql` успешно проверено в отдельной пустой базе PostgreSQL 17.5.** После импорта подтверждены 22 таблицы, пять записей истории миграций и необходимые представление и функции. Таблицы `customers`, `orders`, `AspNetUsers` и `refresh_tokens` в тестовой базе пусты. Проверка выполнялась отдельно от исходной базы; исходная база не изменялась, временная база после проверки удалена.

Сборка, запуск приложения, интеграции и полный сценарий заказа пока не проверены. Полный архив базы с данными в репозиторий не входит. Готовый набор синтетических демоданных пока отсутствует.

## Создание отдельной базы

Используйте PostgreSQL 17 и клиентские утилиты `createdb` / `psql` этой версии. Схема экспортирована из 17.5; совместимость с другими основными версиями не проверена. Команды выполняются из корня репозитория в PowerShell. Замените `YOUR_DB_USER` на свою локальную роль PostgreSQL, имеющую право создать базу. Пароль вводится по запросу утилиты и не хранится в этой инструкции.

```powershell
$pizzeriaDbUser = "YOUR_DB_USER"
createdb --host localhost --username $pizzeriaDbUser --template template0 --encoding UTF8 pizzeria_demo
if ($LASTEXITCODE -ne 0) { throw "Could not create the empty pizzeria_demo database." }

psql --host localhost --username $pizzeriaDbUser --dbname pizzeria_demo -X --set=ON_ERROR_STOP=1 --single-transaction --file database/schema.sql
if ($LASTEXITCODE -ne 0) { throw "Schema import failed. Do not continue with application startup." }

psql --host localhost --username $pizzeriaDbUser --dbname pizzeria_demo -X --set=ON_ERROR_STOP=1 --file database/migrations-history.sql
if ($LASTEXITCODE -ne 0) { throw "Migration history import failed." }
```

`pizzeria_demo` — имя новой базы латиницей; внутри неё создаётся схема `pizzeria`. Если база уже существует, первая команда остановит последовательность. Не применяйте этот файл к используемой базе: экспорт содержит создание объектов и предназначен для отдельной пустой базы. При ошибке импорта сначала выясните причину, не продолжайте со следующими командами.

История миграций импортируется **после схемы**, поскольку её таблица создаётся в первом файле. Экспорт схемы сам по себе не содержит строки истории. **Не запускайте `dotnet ef database update` как дополнительный шаг установки:** схема уже отражает состояние исходной базы, а имеющиеся файлы миграций не являются её полной начальной спецификацией. Дальнейшие изменения модели и миграции требуют отдельной сверки на тестовой базе.

## Какие данные ещё нужны

После импорта таблицы предметной области и Identity пусты. Существующий [DevIdentitySeed](../backend/Pizzeria/Services/DevIdentitySeed.cs) может создать администратора, роли и сотрудников из локальной секции `Seed`, но не заполняет меню, ингредиенты, рецепты или заказы.

1. Задайте `Seed:Admin:Email` и собственный пароль. На новой базе с пустым паролем администратора инициализация завершится до создания ролей и сотрудников, даже если массивы сотрудников заполнены.
2. Для проверки всего процесса добавьте по учебному сотруднику в `Seed:Couriers`, `Seed:Cooks` и `Seed:Collectors` (поля `Email`, `Name`, `Password`). Эти значения храните только локально. Seed связывает созданных пользователей с ролями и записями сотрудников; администратору создаёт профиль клиента.
3. После успешного запуска подготовьте синтетические пиццы и активные позиции меню с ценами. Код административного создания меню сначала создаёт пиццу, затем связанную запись `menu`. Для проверки состава отдельно добавьте ингредиенты и рецепты. Учебного клиента можно создать через регистрацию.
4. Не вставляйте заказы с произвольными идентификаторами: внешние ключи требуют существующего клиента и пицц, доставка и рейс — сотрудника, рецепт — пиццу и ингредиент. Инициализацию всех этих сценариев ещё предстоит проверить на импортированной базе.

Наличие структуры и seed-кода пока не означает, что полный пользовательский сценарий воспроизводится без доработки.

## Локальные настройки

1. Установить .NET SDK 8, PostgreSQL 17 и Node.js, удовлетворяющий требованиям Vite 7. Требование Vite можно проверить в `frontend/package-lock.json` (`node_modules/vite` → `engines`).
2. Применить схему и историю в отдельную базу `pizzeria_demo` по инструкции выше.
3. Скопировать `backend/Pizzeria/appsettings.example.json` в `backend/Pizzeria/appsettings.Development.json` и заполнить локально. Файл назначения исключён из Git.
4. Скопировать `frontend/.env.example` в `frontend/.env`. Адрес API по умолчанию — `https://localhost:7020`.

Обязательные параметры сервера:

- `ConnectionStrings:PizzeriaDb` — подключение к подготовленной PostgreSQL. В скопированном примере замените `Database=pizzeria` на `Database=pizzeria_demo`, укажите свою роль и пароль, сохраните `Search Path=pizzeria,public`. Все Identity-таблицы в этом экспорте находятся в `pizzeria`; функции расчёта суммы тоже используют имена без указания схемы. Поэтому `Search Path` нужен для корректного поиска объектов.
- `Jwt:Key` — собственное случайное секретное значение длиной не менее 32 байт; пустой ключ не допускается. Не использовать общедоступный пример в качестве ключа.
- `Jwt:Issuer` — одинаковое значение для выдачи и проверки токенов внутри приложения.

Параметры отдельных функций:

- `Seed:Admin` и массивы `Seed:Couriers`, `Seed:Cooks`, `Seed:Collectors` задают учебные учётные записи. У сотрудника поля `Email`, `Name`, `Password`. Пароли не включены в пример. Инициализация обращается к таблицам при старте приложения: пустой пароль не отменяет необходимости подготовленной БД.
- `GraphHopper:ApiKey`, `PizzeriaLat`, `PizzeriaLng` — ключ сервиса и фактическая точка начала маршрута. Нулевые координаты в примере — заглушки, которые нужно заменить.
- `Nominatim:UserAgent` — идентификатор приложения с действительным контактным адресом для запросов геокодирования. Заполнить своим контактом и учитывать правила используемого сервиса.
- `Email` — параметры SMTP. По умолчанию уведомления отключены (`Enabled: false`).

Секретные значения можно хранить через .NET user-secrets или переменные окружения вместо файлов. Например, ключу `Jwt:Key` соответствует переменная `Jwt__Key`, а строке подключения — `ConnectionStrings__PizzeriaDb`. Содержимое `VITE_*` попадает в браузерную сборку: помещать туда секреты нельзя.

В публикации используется отдельный `UserSecretsId`, чтобы не привязывать её к прежней локальной конфигурации автора.

## Команды после восстановления базы

Из корня репозитория, PowerShell:

```powershell
dotnet restore backend/Pizzeria.sln
dotnet build backend/Pizzeria.sln
dotnet dev-certs https --trust
$env:ASPNETCORE_ENVIRONMENT = "Development"
dotnet run --project backend/Pizzeria --no-launch-profile --urls "https://localhost:7020"
```

В отдельном терминале:

```powershell
cd frontend
npm ci
npm run dev
```

Интерфейс ожидается на `http://localhost:5173`, Swagger в Development — на `https://localhost:7020/swagger`. Разрешённый CORS origin и порт Vite сейчас фиксированы для локальной разработки. При изменении адресов нужно согласовать `Program.cs`, `vite.config.js` и `VITE_API_URL`.

Дополнительные команды интерфейса: `npm run build` и `npm run lint`. Их наличие в манифесте не означает, что проверки прошли для этой публикации.

## Проверка после восстановления

Импорт опубликованной структуры уже проверен на PostgreSQL 17.5. В своём окружении также убедитесь, что обе команды `psql` завершились без ошибок, прежде чем запускать приложение. Далее требуется сверка работы кода с базой. Известное расхождение для проверки: `orders.geocoded_at` экспортирован как `timestamp with time zone`, а EF-модель задаёт `timestamp without time zone`. Совместимость сохранения дат с текущим кодом ещё не подтверждена; изменение модели или схемы следует проверять отдельно.

Рекомендуемый ручной сценарий: зарегистрировать учебного клиента → создать заказ с двумя позициями → отметить готовность позиций поваром → принять обе позиции сборщиком → упаковать → взять заказ курьером → завершить доставку → сверить статусы клиента и администратора.

Отдельно проверить запрет упаковки неполного заказа, отмену после приготовления позиции, доставку без начатой смены, повторную обработку завершённой доставки и доступ пользователя к чужим заказам. Эти проверки пока не выполнены и не являются заявлением о корректности всех веток.
