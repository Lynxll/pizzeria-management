# Подготовка окружения

## Текущее состояние

Репозиторий содержит код, манифесты зависимостей и имеющиеся миграции. Он пока **не обеспечивает воспроизводимый запуск с пустой базы**. Сборка, подключение к PostgreSQL и интеграции при подготовке публикации не запускались.

Необходимо восстановить исходную базовую схему PostgreSQL. Модели и миграции служат материалом для её сверки, но не заменяют отсутствующий SQL. В частности, приложение использует:

- схему `pizzeria`, таблицы предметной области и Identity;
- PostgreSQL enum-типы из `Data/ModelsEnums.cs`;
- функцию `pizzeria.sync_order_total`, которую часть вызовов использует без указания схемы;
- представление `pizzeria.v_order_finance`;
- изменения колонок и сущностей из существующих миграций.

В примере строки подключения указан `Search Path=pizzeria,public` для вызовов функции без схемы. Нельзя считать, что простое `dotnet ef database update` создаст все необходимые объекты: это нужно проверить после восстановления исходной схемы. Не следует применять миграции к единственной копии рабочей базы.

## Локальные настройки

1. Установить .NET SDK 8, PostgreSQL и Node.js, удовлетворяющий требованиям Vite 7. Требование Vite можно проверить в `frontend/package-lock.json` (`node_modules/vite` → `engines`).
2. Восстановить и проверить схему в отдельной учебной базе, использовать синтетические данные.
3. Скопировать `backend/Pizzeria/appsettings.example.json` в `backend/Pizzeria/appsettings.Development.json` и заполнить локально. Файл назначения исключён из Git.
4. Скопировать `frontend/.env.example` в `frontend/.env`. Адрес API по умолчанию — `https://localhost:7020`.

Обязательные параметры сервера:

- `ConnectionStrings:PizzeriaDb` — подключение к подготовленной PostgreSQL.
- `Jwt:Key` — собственное случайное секретное значение длиной не менее 32 байт; пустой ключ не допускается. Не использовать общедоступный пример в качестве ключа.
- `Jwt:Issuer` — одинаковое значение для выдачи и проверки токенов внутри приложения.

Параметры отдельных функций:

- `Seed:Admin` и массивы `Seed:Couriers`, `Seed:Cooks`, `Seed:Collectors` задают учебные учётные записи. У сотрудника поля `Email`, `Name`, `Password`. Пароли не включены в пример. Инициализация обращается к таблицам при старте приложения: пустой пароль не отменяет необходимости подготовленной БД.
- `GraphHopper:ApiKey`, `PizzeriaLat`, `PizzeriaLng` — ключ сервиса и фактическая точка начала маршрута. Нулевые координаты в примере — заглушки, которые нужно заменить.
- `Nominatim:UserAgent` — идентификатор приложения с действительным контактным адресом для запросов геокодирования. Заполнить своим контактом и учитывать правила используемого сервиса.
- `Email` — параметры SMTP. По умолчанию уведомления отключены (`Enabled: false`).

Секретные значения можно хранить через .NET user-secrets или переменные окружения вместо файлов. Например, ключу `Jwt:Key` соответствует переменная `Jwt__Key`, а строке подключения — `ConnectionStrings__PizzeriaDb`. Содержимое `VITE_*` попадает в браузерную сборку: помещать туда секреты нельзя.

В публикации используется отдельный `UserSecretsId`, чтобы не привязывать её к прежней локальной конфигурации автора.

## Команды после восстановления базы

Из корня репозитория, PowerShell:

```powershell
dotnet restore backend/Pizzeria.sln
dotnet build backend/Pizzeria.sln
dotnet dev-certs https --trust
$env:ASPNETCORE_ENVIRONMENT = "Development"
dotnet run --project backend/Pizzeria --no-launch-profile --urls "https://localhost:7020"
```

В отдельном терминале:

```powershell
cd frontend
npm ci
npm run dev
```

Интерфейс ожидается на `http://localhost:5173`, Swagger в Development — на `https://localhost:7020/swagger`. Разрешённый CORS origin и порт Vite сейчас фиксированы для локальной разработки. При изменении адресов нужно согласовать `Program.cs`, `vite.config.js` и `VITE_API_URL`.

Дополнительные команды интерфейса: `npm run build` и `npm run lint`. Их наличие в манифесте не означает, что проверки прошли для этой публикации.

## Проверка после восстановления

Рекомендуемый ручной сценарий: зарегистрировать учебного клиента → создать заказ с двумя позициями → отметить готовность позиций поваром → принять обе позиции сборщиком → упаковать → взять заказ курьером → завершить доставку → сверить статусы клиента и администратора.

Отдельно проверить запрет упаковки неполного заказа, отмену после приготовления позиции, доставку без начатой смены, повторную обработку завершённой доставки и доступ пользователя к чужим заказам. Эти проверки пока не выполнены и не являются заявлением о корректности всех веток.
